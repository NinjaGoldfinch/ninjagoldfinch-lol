# Monitoring hooks

What ninjagoldfinch.lol exposes for monitoring: its health, version and status endpoints, the events it sends, the log lines it writes, and what ninja-monitor watches. Most of it is small on purpose; gaps are marked.

## Endpoints

| Endpoint           | Exists | Behaviour                                                                                                                                                                                                                                                                                                                   | Source                                                                                     |
| ------------------ | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `GET /healthz`     | yes    | `200 {"ok":true,"version":"…"}`, `Cache-Control: no-store`. Liveness only: answers while the Node process serves HTTP, without calling riot-proxy. `version` is `package.json`'s at build time, so a deploy can wait for the release it activated (ADR-051)                                                                 | `src/routes/healthz/+server.ts:6-9`                                                        |
| `GET /api/version` | yes    | `{"version":"…","commit":"…"}`, public, `no-store`: the build's identity, `dev` for both in a build that is not a release (ADR-061)                                                                                                                                                                                         | `src/routes/api/version/+server.ts:9-10`                                                   |
| `GET /api/status`  | yes    | The shared status contract (ADR-062): `riot_proxy` and `static_data` checks, run in the background every `STATUS_CHECK_INTERVAL_S` and held, and the request and riot-proxy counters. A bearer `STATUS_TOKEN`, or a request from the host or `STATUS_ALLOW_CIDR`; `401` otherwise. Shape and settings in `README.md:99-151` | `src/routes/api/status/+server.ts:10-34`, `src/lib/server/status.ts:55-75,100-131,148-170` |
| readiness          | partly | No endpoint of its own. `/api/status`'s `riot_proxy` check probes riot-proxy's `/readyz` with the site's key, so it shows riot-proxy unreachable, not ready, or refusing the key                                                                                                                                            | `src/lib/server/status.ts:55-75`                                                           |
| metrics            | partly | No Prometheus endpoint; counters and gauges in `/api/status`'s `metrics`                                                                                                                                                                                                                                                    | `src/lib/server/metrics.ts`                                                                |

`/healthz` is used by Playwright to know the server is up (`playwright.config.ts:20`), by the deploy, whose `ninja-deploy` health check polls `http://127.0.0.1:3000/healthz` until it reports the new release's version and rolls back otherwise (`README.md:88`, ADR-051, ADR-053), and by staging's smoke test (ADR-060). On production it is reachable only on the host (`curl -s http://127.0.0.1:3000/healthz`) or through the Tunnel at `https://ninjagoldfinch.lol/healthz`.

To check the dependency the site cannot run without, probe riot-proxy's own readiness, `GET http://127.0.0.1:8080/readyz` (200 or 503 with `sqlite`, `limiter`, reader and writer status and its version; no key, no quota) (`riot-proxy:src/routes/health.rs:1,73-150`).

The site also POSTs events on changes of state (`proxy_unreachable`, `proxy_recovered`, `deployed`) to `EVENTS_URL` when it is set (ADR-063; `README.md:153-179`).

## ninja-monitor

ninja-monitor is a separate service; this repo has no code for it. riot-proxy's hosting notes describe its checks on `ngf-prod-syd1` (`riot-proxy:docs/design/12-object-storage-and-hosting.md:839-845`):

| Check                              | Threshold                          |
| ---------------------------------- | ---------------------------------- |
| `ninjagoldfinch-lol` down          | after 30 s, repeating every 30 min |
| `ninjagoldfinch-lol` memory        | limit 1 GiB                        |
| `riot-proxy`, `cloudflared` memory | 2 GiB, 512 MiB                     |
| host memory                        | below 15 % free                    |
| disk                               | above 70 % and 85 %                |
| host CPU                           | above 90 % for 20 min              |

Alerts go to a Discord webhook; its API is reached over an SSH local forward. The systemd unit restarts the site 2 s after any exit (`Restart=always`, `RestartSec=2`, owner-supplied unit), so a crash loop shows as repeated restarts rather than a long outage.

A second ninja-monitor runs on `ngf-mon-syd1`, the monitoring host, watching that host and posting to a Discord webhook of its own (`riot-proxy:docs/design/12-object-storage-and-hosting.md:839-840,850-851`). That host also runs the site's staging copy (ADR-057).

### From outside: the heartbeat to Healthchecks.io

What is known (P5-05, owner 2026-11-09; `docs/PROGRESS.md`, "P5-05 check"): a heartbeat from `ngf-mon-syd1` pings a Healthchecks.io check every minute, and Healthchecks.io emails the owner when the pings stop, with 5 minutes of grace after the check's period.

What ninja-monitor's public repository settles (`NinjaGoldfinch/ninja-monitor` at `v0.2.3`, which was also its default branch on 2026-11-09):

- Its heartbeat is a GET to one secret URL, read from an environment variable (`NINJA_MONITOR_HEARTBEAT_URL`), every `interval`, 60 s by default. Any 2xx counts; a failure is logged and otherwise ignored. It runs on its own timer, independent of sampling and alerts (`ninja-monitor:src/heartbeat.rs:1-28`, `ninja-monitor:src/config.rs:143-161`, `ninja-monitor:README.md:279-281`).
- ninja-ingest, the central server in the same repository, has a heartbeat of its own: also a GET every 60 s by default, sent only after a query to its database answers (`ninja-monitor:ingest/src/heartbeat.rs:1-48`, `ninja-monitor:ingest/src/config.rs:110-127`).
- Neither can be set to fetch any other URL. ninja-monitor's configuration has the sections `server`, `sampling`, `paths`, `host`, `service`, `discord`, `heartbeat`, `push` and `alert`, and refuses unknown keys (`ninja-monitor:src/config.rs:14-35`). A service is watched through its systemd unit's cgroup, not over HTTP, and `down` means the unit is not running (`ninja-monitor:src/config.rs:106-116`, `ninja-monitor:src/alerts/mod.rs:175-178`). The only `/healthz` it requests is a ninja-ingest server's, from `--check` (`ninja-monitor:src/check.rs:88-111`).

## Suggested alert conditions from the logs

These are derived from the log lines above; none is configured anywhere in this repo.

| Condition                                             | Likely cause                                              |
| ----------------------------------------------------- | --------------------------------------------------------- |
| Many `proxy unreachable`                              | riot-proxy down                                           |
| Many `proxy timeout`                                  | riot-proxy hung or overloaded                             |
| `proxy 401` or `proxy 403`                            | `PROXY_KEY` revoked, wrong or lacking `read`              |
| `proxy 429` with `QUOTA_EXCEEDED` in riot-proxy's log | The key's `quota_per_min` is too low for traffic          |
| Repeated `proxy slow … x-cache=MISS`                  | riot-proxy analytics not warmed after a rebuild           |
| Repeated `slow load` for one route                    | A riot-proxy call on that page is slow; the line names it |
| `unexpected … payload`                                | riot-proxy or Riot changed a payload shape                |
